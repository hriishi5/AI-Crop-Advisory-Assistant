# AI-Powered Agriculture Crop Advisory Assistant — Master Build Prompt

## 1. Header & System Persona Role

You are a **Senior Full-Stack Engineer and AI Systems Architect** operating inside an autonomous coding agent environment (Cursor / Claude Code / Replit Agent / Bolt). You have full read/write access to the project's filesystem, terminal, package manager, and database provisioning tools. You do not ask clarifying questions — you make sound engineering decisions and proceed. You build production-grade, deployable software, not prototypes or demos. Every file you generate must be complete, syntactically valid, and free of `// TODO`, `// implement later`, or placeholder logic. If a decision is not specified below, you resolve it using industry best practice and document the decision in a code comment at the point of use.

Your task in this session is to build, end-to-end, the **AI-Powered Agriculture Crop Advisory Assistant** described in this document.

---

## 2. Core Mission Directive

Build a fully functional, multi-user, AI-driven web application that helps farmers and agricultural extension workers get **personalized, real-time crop advisory** — covering crop selection, soil health interpretation, irrigation and fertilizer scheduling, pest/disease diagnosis from symptom text, and market-linked sowing/harvest timing — by combining structured farmer input (location, soil type, land size, season, crop history) with Google's Gemini AI reasoning, and persisting every advisory session so farmers can revisit past recommendations, track their farms, and see how conditions change season to season.

Do not stop at a chat interface. Build a structured, form-driven advisory workflow backed by a normalized relational schema, secure multi-tenant data isolation, and typed request/response validation end-to-end.

---

## 3. Product Goal

Enable a smallholder or mid-size farmer with minimal technical literacy to:

1. Register a free account and add one or more **farms** (plot-level records with location, soil type, and area).
2. Submit a **crop advisory request** for a farm by filling a short structured form (season, budget tier, irrigation availability, previous crop, known soil issues).
3. Receive a **structured AI-generated advisory report** — not a wall of text — containing ranked crop recommendations, a fertilizer/irrigation schedule, risk flags, and estimated cost-to-yield guidance, each grounded in the specific inputs supplied.
4. Separately submit a **pest/disease diagnostic query** by describing symptoms (and optionally uploading a photo description as text) and get a structured diagnosis with confidence level, likely causes, and organic + chemical treatment options.
5. View a **dashboard** of all past advisories per farm, so recommendations compound in usefulness over multiple seasons.
6. Have full data isolation — one farmer must never be able to see another farmer's farms, advisories, or diagnostic history, enforced at the database layer, not just the UI.

## 4. Mandatory Features

- Email + password authentication (registration, login, logout, session persistence via JWT in HTTP-only cookies).
- Farmer profile management (name, phone, primary language, default location).
- Farm CRUD: create, list, edit, archive (soft-delete) farms belonging to the logged-in farmer only.
- Crop Advisory workflow: structured intake form → Gemini-powered structured recommendation → persisted advisory record → viewable history.
- Pest & Disease Diagnostic workflow: structured symptom intake form → Gemini-powered structured diagnosis → persisted diagnostic record → viewable history.
- Dashboard aggregating: total farms, total advisories generated, most recent advisory per farm, and any open/unresolved diagnostic flags.
- Advisory detail view with full breakdown (recommended crops, fertilizer plan, irrigation plan, risk factors, confidence score).
- Diagnostic detail view with full breakdown (likely disease/pest, confidence, symptoms matched, treatment plan, prevention tips).
- Search/filter advisory and diagnostic history by farm, crop, and date range.
- Responsive UI (mobile-first — this is a farmer-facing tool, majority usage will be on Android phones in the field).
- Graceful handling and clear surfacing of AI service failures (timeout, rate limit, malformed response) without ever showing the user a raw stack trace.
- Server-side rate limiting on all AI-invoking endpoints to control cost and abuse.

## 7. User Flow

1. **Landing → Register/Login** → JWT issued, stored as HTTP-only cookie → redirect to `/dashboard`.
2. **Dashboard** shows "Add your first farm" prompt if the farmer has zero farms.
3. Farmer navigates to **`/farms`**, adds a farm (name, village/district/state, GPS-optional, soil type, area in acres, primary irrigation source).
4. From a farm's detail page, farmer clicks **"Get Crop Advisory"** → structured intake form (`/farms/:farmId/advisory/new`) → submit → backend calls Gemini with a structured system + user prompt → Gemini returns strict JSON → backend validates with Zod → persists to `crop_advisories` table → frontend redirects to `/advisory/:advisoryId` to render the structured report.
5. From the same farm, farmer can click **"Diagnose a Problem"** → symptom intake form (`/farms/:farmId/diagnose/new`) → submit → backend calls Gemini with a diagnostic system + user prompt → Gemini returns strict JSON → backend validates with Zod → persists to `pest_diagnostics` table → frontend redirects to `/diagnostic/:diagnosticId`.
6. Farmer can revisit `/history` at any time to search past advisories/diagnostics across all their farms, filtered by crop, farm, or date.
7. Farmer can edit their profile at `/profile` at any time; changes do not require re-authentication.
8. On logout, the JWT cookie is cleared and the farmer is redirected to `/`.

## 8. Target Domains & Categorization

The AI advisory logic must reason within these fixed domains — do not let the model free-associate outside them:

- **Crop categories:** Cereals (rice, wheat, maize, millets), Pulses (chickpea, pigeon pea, lentil), Oilseeds (groundnut, mustard, soybean, sunflower), Vegetables (tomato, onion, potato, brinjal, okra), Cash crops (cotton, sugarcane), Fruits (banana, mango, citrus — for perennial-plot advisories only).
- **Soil types:** Alluvial, Black (regur), Red, Laterite, Arid/Desert, Mountain/Forest, Saline/Alkaline.
- **Seasons:** Kharif (June–Oct), Rabi (Oct–Mar), Zaid/Summer (Mar–June).
- **Irrigation availability:** Rainfed only, Canal, Borewell/Tubewell, Drip/Sprinkler, Mixed.
- **Budget tiers:** Low (minimal input cost, subsistence-oriented), Medium (balanced input/output), High (commercial, high-input high-yield).
- **Pest/disease query categories:** Fungal, Bacterial, Viral, Insect/Pest infestation, Nutrient deficiency (symptom overlap with disease), Nematode, Weed competition.

This taxonomy is authoritative and drives both form dropdown options and the enum constraints in the database schema and Zod schemas.

## 10. Database Schema (Production SQL for PostgreSQL)

```sql
-- ============================================================
-- AI-Powered Agriculture Crop Advisory Assistant — Schema
-- ============================================================

CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- ---------- FARMERS ----------
CREATE TABLE farmers (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    full_name         VARCHAR(120) NOT NULL,
    email             VARCHAR(255) NOT NULL UNIQUE,
    password_hash     TEXT NOT NULL,
    phone             VARCHAR(20),
    primary_language  VARCHAR(40) DEFAULT 'en',
    default_state     VARCHAR(80),
    default_district  VARCHAR(80),
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ---------- FARMS ----------
CREATE TABLE farms (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    farmer_id             UUID NOT NULL REFERENCES farmers(id) ON DELETE CASCADE,
    name                  VARCHAR(120) NOT NULL,
    village               VARCHAR(120),
    district              VARCHAR(80),
    state                 VARCHAR(80),
    gps_lat               NUMERIC(9,6),
    gps_lng               NUMERIC(9,6),
    soil_type             VARCHAR(30) NOT NULL CHECK (soil_type IN
                              ('alluvial','black','red','laterite','arid','mountain','saline_alkaline')),
    area_acres            NUMERIC(8,2) NOT NULL CHECK (area_acres > 0),
    primary_irrigation    VARCHAR(30) NOT NULL CHECK (primary_irrigation IN
                              ('rainfed','canal','borewell','drip_sprinkler','mixed')),
    is_archived           BOOLEAN NOT NULL DEFAULT false,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_farms_farmer_id ON farms(farmer_id);

-- ---------- CROP ADVISORIES ----------
CREATE TABLE crop_advisories (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    farm_id               UUID NOT NULL REFERENCES farms(id) ON DELETE CASCADE,
    farmer_id             UUID NOT NULL REFERENCES farmers(id) ON DELETE CASCADE,
    season                VARCHAR(10) NOT NULL CHECK (season IN ('kharif','rabi','zaid')),
    soil_type_used        VARCHAR(30) NOT NULL,
    land_area_acres_used  NUMERIC(8,2) NOT NULL,
    irrigation_used        VARCHAR(30) NOT NULL,
    budget_tier           VARCHAR(10) NOT NULL CHECK (budget_tier IN ('low','medium','high')),
    previous_crop         VARCHAR(80),
    known_soil_issues     TEXT[] DEFAULT '{}',
    farmer_goal            VARCHAR(30) NOT NULL,
    additional_notes       TEXT,
    ai_raw_response         JSONB NOT NULL,
    recommended_crops       JSONB NOT NULL,
    fertilizer_plan          JSONB NOT NULL,
    irrigation_plan          JSONB NOT NULL,
    risk_factors             JSONB NOT NULL,
    confidence_score        NUMERIC(3,2) CHECK (confidence_score BETWEEN 0 AND 1),
    model_version            VARCHAR(60) NOT NULL,
    created_at               TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_advisories_farm_id ON crop_advisories(farm_id);
CREATE INDEX idx_advisories_farmer_id ON crop_advisories(farmer_id);
CREATE INDEX idx_advisories_created_at ON crop_advisories(created_at DESC);

-- ---------- PEST / DISEASE DIAGNOSTICS ----------
CREATE TABLE pest_diagnostics (
    id                        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    farm_id                   UUID NOT NULL REFERENCES farms(id) ON DELETE CASCADE,
    farmer_id                 UUID NOT NULL REFERENCES farmers(id) ON DELETE CASCADE,
    affected_crop             VARCHAR(80) NOT NULL,
    growth_stage              VARCHAR(20) NOT NULL CHECK (growth_stage IN
                                  ('seedling','vegetative','flowering','fruiting','maturity')),
    symptom_category          VARCHAR(30),
    symptom_description        TEXT NOT NULL,
    affected_plant_part        TEXT[] NOT NULL,
    days_since_symptoms        INTEGER,
    weather_recent              VARCHAR(20),
    ai_raw_response              JSONB NOT NULL,
    likely_diagnosis             VARCHAR(150) NOT NULL,
    confidence_score             NUMERIC(3,2) CHECK (confidence_score BETWEEN 0 AND 1),
    possible_causes                JSONB NOT NULL,
    treatment_plan                 JSONB NOT NULL,
    prevention_tips                 JSONB NOT NULL,
    is_resolved                     BOOLEAN NOT NULL DEFAULT false,
    model_version                    VARCHAR(60) NOT NULL,
    created_at                        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_diagnostics_farm_id ON pest_diagnostics(farm_id);
CREATE INDEX idx_diagnostics_farmer_id ON pest_diagnostics(farmer_id);
CREATE INDEX idx_diagnostics_created_at ON pest_diagnostics(created_at DESC);

-- ---------- UPDATED_AT TRIGGER ----------
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_farmers_updated_at BEFORE UPDATE ON farmers
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER trg_farms_updated_at BEFORE UPDATE ON farms
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

## 11. Row Level Security (RLS) / Data Isolation Rules

Replit Postgres connections in this stack are made via a pooled service connection, not per-user database roles, so **true Postgres RLS policies are optional but recommended as defense-in-depth**. Implement both layers:

### 11.1 Application-layer isolation (mandatory)
Every single query touching `farms`, `crop_advisories`, or `pest_diagnostics` MUST be scoped by `farmer_id` (or a join through `farm_id → farms.farmer_id`) derived **only** from the authenticated JWT session — never from a client-supplied `farmerId` field in the request body or query string. Write this as a single reusable data-access helper (e.g. `assertFarmOwnership(farmId, farmerId)`) called at the top of every controller that operates on a farm-scoped resource, before any DB write or read.

### 11.2 Database-layer RLS (defense-in-depth, implement if using per-role connections; otherwise document as future hardening)
```sql
ALTER TABLE farms ENABLE ROW LEVEL SECURITY;
ALTER TABLE crop_advisories ENABLE ROW LEVEL SECURITY;
ALTER TABLE pest_diagnostics ENABLE ROW LEVEL SECURITY;

CREATE POLICY farms_isolation ON farms
    USING (farmer_id = current_setting('app.current_farmer_id')::uuid);

CREATE POLICY advisories_isolation ON crop_advisories
    USING (farmer_id = current_setting('app.current_farmer_id')::uuid);

CREATE POLICY diagnostics_isolation ON pest_diagnostics
    USING (farmer_id = current_setting('app.current_farmer_id')::uuid);
```
If RLS is enabled, the Express connection middleware must run `SET app.current_farmer_id = '<uuid>'` at the start of every authenticated request using a transaction-scoped `SET LOCAL` inside the connection pool client, sourced from the verified JWT payload.

### 11.3 Non-negotiable rules
- Never trust a `farmerId` or `farmId` passed in a request body for authorization decisions — only for identifying *which* resource, after ownership is verified server-side.
- All archive/delete operations are soft-deletes (`is_archived = true`) — never hard `DELETE` a farm with advisory history.
- Passwords are hashed with `bcrypt` (cost factor 12) and never logged, returned in any API response, or stored in plaintext anywhere, including error logs.

## 13. Gemini SDK Setup & Server-Side Security

- The `@google/genai` client is instantiated **exactly once**, server-side only, in `server/services/geminiClient.ts`. It is never imported into any frontend file, and the API key is never sent to the client in any form (no env var prefixed `VITE_` or `REACT_APP_` for this key).
- API key is read from `process.env.GEMINI_API_KEY` at server startup; if missing, the server fails fast with a clear startup error rather than failing silently on first request.
- All Gemini calls use the SDK's structured/JSON output mode (`responseMimeType: "application/json"` with a `responseSchema`) so the model is constrained to emit valid JSON matching the shapes defined in Section 15 — never free-form text that is then regex-parsed.
- Every Gemini call is wrapped in a `try/catch` with:
  - A request timeout (10s) via `AbortController`.
  - Exactly one retry on transient failure (5xx, timeout) with exponential backoff, then fail to a typed `AIServiceError`.
  - The raw model response is stored in the `ai_raw_response` JSONB column for auditability, even though the structured/parsed fields are what the frontend renders.
- Server-side rate limiting (`express-rate-limit`) is applied specifically to `/advisories` and `/diagnostics` POST routes — e.g. 10 requests per farmer per hour — separate from any general API rate limit, because these are the cost-bearing AI-invoking endpoints.
- Input passed into the Gemini prompt is always the **validated, typed Zod output** of the intake form — never raw unvalidated `req.body` — to prevent prompt injection via malformed or oversized fields.

## 14. AI System Prompt

Two distinct system prompts are used — one per workflow — each passed as the `systemInstruction` on the Gemini client call.

### 14.1 Crop Advisory System Prompt
```
You are an expert agronomist and agricultural extension officer with deep,
practical knowledge of Indian farming conditions, soil science, crop
rotation, and input economics. You give advice calibrated to smallholder
and mid-size farmers, not industrial agribusiness.

Rules you must follow:
1. Base every recommendation strictly on the structured inputs provided —
   season, soil type, land area, irrigation availability, budget tier,
   previous crop, known soil issues, and the farmer's stated goal.
2. Recommend 2 to 4 crops, ranked, each with a clear justification tied to
   the specific inputs (not generic crop trivia).
3. Never recommend a crop requiring irrigation the farmer does not have
   available.
4. Flag any risk implied by the previous crop (e.g. same-family crop
   rotation disease risk, nutrient depletion) explicitly in risk_factors.
5. Fertilizer and irrigation plans must be stage-based (sowing, vegetative,
   flowering, maturity) and quantified in practical units (kg/acre,
   liters/acre or irrigation frequency), not vague ("water regularly").
6. If known_soil_issues indicates salinity, waterlogging, or low organic
   matter, that constraint overrides yield-maximizing crop choices.
7. Output ONLY valid JSON matching the exact schema provided. No prose
   outside the JSON. No markdown code fences.
8. Set confidence_score lower (below 0.6) when inputs are sparse or
   conflicting; do not overstate certainty.
```

### 14.2 Pest/Disease Diagnostic System Prompt
```
You are an expert plant pathologist and entomologist specializing in
field-crop and vegetable pest/disease diagnosis from farmer-reported
symptoms, without laboratory confirmation.

Rules you must follow:
1. Reason from the described symptoms, affected plant part, growth stage,
   days since onset, and recent weather to identify the most likely cause.
2. Always list at least 2 possible_causes ranked by likelihood, even when
   one is dominant — symptom-based diagnosis without lab testing is
   inherently uncertain, and you must reflect that honestly.
3. Distinguish clearly between disease, pest, and nutrient-deficiency
   causes when symptoms overlap (e.g. yellowing leaves can be nitrogen
   deficiency OR a viral infection) rather than picking one prematurely.
4. Every treatment_plan must include both an organic/cultural option and a
   chemical option where applicable, each with dosage or application
   guidance in practical terms.
5. Always include prevention_tips for future seasons, not just treatment
   for the current outbreak.
6. If symptom_description is vague or generic, set confidence_score below
   0.5 and explicitly recommend the farmer consult a local agricultural
   extension officer or send a photo for visual confirmation.
7. Output ONLY valid JSON matching the exact schema provided. No prose
   outside the JSON. No markdown code fences.
8. Never recommend a banned or restricted-use pesticide.
```

## 16. Zod Validation Requirements

Define all schemas in a single shared file, `shared/schemas.ts`, imported by both frontend (form validation via `@hookform/resolvers/zod`) and backend (request body validation middleware).

```typescript
import { z } from "zod";

export const seasonEnum = z.enum(["kharif", "rabi", "zaid"]);
export const soilTypeEnum = z.enum([
  "alluvial", "black", "red", "laterite", "arid", "mountain", "saline_alkaline",
]);
export const irrigationEnum = z.enum([
```

## 18. Security Requirements

- Passwords hashed with `bcrypt`, cost factor ≥ 12; never returned in any API response.
- JWT stored in `HttpOnly`, `Secure`, `SameSite=Strict` cookie — never in `localStorage`.
- All mutating endpoints (`POST`, `PATCH`, `DELETE`) require CSRF protection appropriate to cookie-based auth (double-submit token or `SameSite=Strict` + origin check).
- All inputs validated server-side with Zod even though client-side validation exists — client validation is a UX convenience, never a security boundary.
- Ownership checks (Section 11) run before every read or write to `farms`, `crop_advisories`, `pest_diagnostics`.
- Rate limiting on `/auth/login` (prevent brute force) and on AI-invoking routes (prevent cost abuse).
- Helmet middleware for standard HTTP security headers.
- No secrets, API keys, or connection strings in frontend bundles — audited via a build-time check that fails the build if `GEMINI_API_KEY` or `DATABASE_URL` appear in any `dist/` output.
- SQL access exclusively through parameterized queries or the query builder/ORM — string-concatenated SQL is forbidden.
- Generic error messages returned to the client (`"Something went wrong. Please try again."`); full error detail logged server-side only.

## 21. Implementation Phases

**Phase 1 — Foundation**
Scaffold client + server + shared workspaces, configure TypeScript, Tailwind, Vite proxy to Express. Provision Replit Postgres, run `schema.sql`, verify connection pool.

**Phase 2 — Auth & Profile**
Implement register/login/logout/me, JWT cookie issuance, `authenticate` middleware, `ProtectedRoute` on frontend, `ProfileForm`.

**Phase 3 — Farms CRUD**
Implement farms routes with ownership middleware, `FarmList`/`FarmForm`/`FarmCard`, farm detail page shell.

**Phase 4 — Crop Advisory Pipeline**
Build `geminiClient.ts`, advisory system prompt + user prompt template, Zod schemas for intake and AI response, `POST /farms/:farmId/advisories` with retry-on-invalid-JSON logic, `AdvisoryIntakeForm`, `AdvisoryReportView`.

**Phase 5 — Pest/Disease Diagnostic Pipeline**
Mirror Phase 4 for diagnostics: prompt templates, schemas, route, `DiagnosticIntakeForm`, `DiagnosticReportView`, resolve toggle.

**Phase 6 — Dashboard & History**
Implement `/dashboard/summary` and `/history` endpoints with filtering, build `DashboardSummaryCards`, `HistoryFilterBar`, `CombinedHistoryTable`.

**Phase 7 — Security Hardening**
Add rate limiting, Helmet, CSRF protection, generic error handling, audit for secret leakage in the client bundle, confirm ownership checks on every resource route.

**Phase 8 — Polish & QA**
Mobile responsiveness pass, empty states, loading states, AI failure states, end-to-end manual test of both AI pipelines with varied inputs, verify data isolation with two test farmer accounts.

## 22. Acceptance Criteria

- [ ] A new farmer can register, log in, and land on an empty-state dashboard.
- [ ] A farmer can create, edit, and archive a farm; archived farms disappear from `/farms` but their historical advisories remain accessible.
- [ ] Submitting the crop advisory intake form produces a persisted, structured report matching the Section 15.1 schema, rendered (not raw JSON) at `/advisory/:advisoryId`.
- [ ] Submitting the diagnostic intake form produces a persisted, structured report matching the Section 15.2 schema, rendered at `/diagnostic/:diagnosticId`.
- [ ] A second farmer account cannot view, edit, or enumerate the first farmer's farms, advisories, or diagnostics — verified by direct API call with a valid session but a foreign resource ID (must return `403`/`404`, never `200`).
- [ ] All AI-invoking endpoints are rate-limited and return a clear, typed error when the limit is hit.
- [ ] Malformed or schema-violating Gemini output triggers one retry, then a graceful typed error — never a raw crash or unhandled promise rejection.
- [ ] No secret (`GEMINI_API_KEY`, `JWT_SECRET`, `DATABASE_URL`) appears anywhere in the built client bundle.
- [ ] `/history` correctly filters combined advisories + diagnostics by farm, crop, date range, and type.
- [ ] The full UI is usable on a 375px-wide mobile viewport without horizontal scrolling or clipped content.
- [ ] All Zod schemas in `shared/schemas.ts` are imported by both client forms and server route validation — no schema duplication.
